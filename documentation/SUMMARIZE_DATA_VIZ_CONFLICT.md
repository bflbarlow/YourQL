# Summarize Results / Data Visualization Conflict Analysis

> **Date:** 2026-08-12
> **Scope:** Interaction between the "Summarize results" and "Data Visualization" conversation settings in the agentic loop pipeline.
> **Status:** Proposed — not yet implemented. Per `AGENT_READ_FIRST.md` §0 (Document Precedence), this file is a point-in-time technical note; `AGENT_READ_FIRST.md` wins on questions of goal alignment, risk tolerance, and priority. See `RISK_ANALYSIS_LOG.md` for prior, related, already-implemented decisions on the summarization/chart rendering path (2026-08-05 and 2026-08-10 entries) — this proposal builds on, and does not contradict, that history.

---

## 1. Summary

When both "Summarize results" and "Data Visualization" are enabled on a conversation, two issues surface: a functional bug where the chart is silently lost depending on tool-call ordering in a batch, and a UX inconsistency where the summarization text lives in the wrong place in the visual hierarchy. This document traces the full code path, identifies each issue, and proposes a single unified fix.

### Key Design Principle: Summarization IS the Answer

When Summarize is ON, the `summarizeResults()` call **is** the answer text. Any `respond_to_user` calls the LLM happens to emit are irrelevant — they are intentionally ignored. This is by design, not a defect. The summarization feature replaces the LLM's own prose with a structured, data-focused summary generated by a separate LLM call using the full result set. There is no "discarded text" problem to solve; there is no need to make the LLM aware of summarization in the system prompt.

## 3. Issue #1 (🔴 Bug): Chart Silently Lost in Three-Tool Batch

### Location
`pkg/services/agentic_loop.go`, tool-call processing loop (~lines 1260–1550)

### Mechanism
When the LLM batches `query_database(is_exploration=false)`, `respond_to_user`, and `render_chart` in a single message, the rendering outcome depends on the **order** of the tool calls in the LLM's `tool_calls` array:

**Order: query → chart → respond (works correctly)**
```
1. query_database  → pendingFinal set, hasChartInBatch=true, loop continues
2. render_chart    → pendingFinal.render(chartConfig="...")  ✅
3. respond_to_user → pendingFinal is nil → handleRespond() (separate bubble)
```

**Order: query → respond → chart (CHART LOST)**
```
1. query_database  → pendingFinal set, hasChartInBatch=true, loop continues
2. respond_to_user → pendingFinal.render(chartConfig="")  ❌ chart lost!
                     returns immediately — loop exits
3. render_chart    → NEVER REACHED
```

The `query_database` handler checks `hasChartInBatch` to prevent premature return, but the `respond_to_user` handler does **not** check for a pending chart in the same batch. It eagerly consumes `pendingFinal` with an empty chartConfig and returns, leaving `render_chart` unprocessed.

### Why the LLM Produces This Batch
The system prompt explicitly instructs batching with the final query:

| Instruction | Text |
|---|---|
| `instructions.3` | *"Consider pairing `respond_to_user` with your final `query_database`"* |
| `instructions.2c` | *"Must be batched with `query_database` in the SAME message"* |
| `charts.timing` | *"Batch render_chart with query_database (is_exploration: false) in the SAME response"* |

The LLM naturally produces all three in one message, and the tool-call ordering is not controlled by the instructions.

### Impact
- **Frequency:** Occurs whenever the LLM puts `respond_to_user` before `render_chart` in its tool_calls array (~50% probability depending on provider/model behavior)
- **User sees:** Summary text + data table, but no chart — even though the LLM generated one
- **Silent failure:** No error logged, the chart config is simply never used

## 4. Issue #2 (🟡 UX Inconsistency): Summary Lives in the Wrong Visual Position

### Location
- `pkg/services/sql_execution.go`, `ToHTML()` lines 370–398
- `pkg/services/discussion_engine.go`, `summarizeResults()` line ~647

### Mechanism

When both Summarize and Viz are ON, the summary text from `summarizeResults()` is rendered as a top-level `<div class="markdown-content">` **above** the collapsed results table. The summarization prompt tells the summarizing LLM:

> *"Frame your summary as an analysis of the overall result... you are summarizing the full result, which the user sees below."*

But the actual visual is:

```
┌──────────────────────────────┐
│         VizChart             │  ← chart
├──────────────────────────────┤
│  Summary text                │  ← "you are summarizing the full result,
│  "As you can see below..."   │     which the user sees below"
├──────────────────────────────┤
│ ▶ View raw results (45 rows) │  ← table collapsed, user hasn't seen it
└──────────────────────────────┘
```

The summary references data "below" that the user must click to reveal. The summary is the answer text, yet it's separated from the data it summarizes by the expand/collapse boundary. This creates friction: the user reads the summary, sees a reference to data they can't verify without an extra click.

### Impact
- The chart is the visual answer, the summary is the textual answer — they should feel like a unified response
- The summary and the raw data are tightly coupled but visually separated
- When the user expands "View raw results," they see the table but the summary is already scrolled above it

## 5. Proposed Solution: Unified Fix

### Design Decision

When both Summarize and Data Visualization are ON:

1. The **chart** is the primary visual answer — rendered at the top
2. The **summarization** moves inside the "View raw results" expander, placed alongside the raw data table it describes
3. No text appears above the chart — the chart and expander are the complete answer
4. `respond_to_user` text is ignored as it always has been during summarization

### Target Visual Result

```
┌──────────────────────────────────────┐
│            VizChart                  │  ← chart is the primary answer
├──────────────────────────────────────┤
│ ▶ View raw results (45 rows)         │
│   ┌──────────────────────────────┐   │
│   │ Summary text                 │   │  ← summarization lives HERE,
│   │ "The query returned 45..."   │   │     right next to the data
│   │                              │   │
│   │ Raw data table               │   │
│   │ ┌──────┬──────┬──────┐       │   │
│   │ │ col1 │ col2 │ ...  │       │   │
│   │ └──────┴──────┴──────┘       │   │
│   └──────────────────────────────┘   │
└──────────────────────────────────────┘
```

No markdown-content div above the chart. The chart stands alone as the visual answer. The summary and raw table are co-located inside the expander — the user reads the summary and sees the data it references in the same viewport.

### Execution Flow

```
query_database(final)  → results captured, pendingFinal set
render_chart           → chart config captured, rendering DEFERRED
                         (pendingFinal not consumed yet)
summarizeResults()     → blocking LLM call runs
                         ↓
           Everything assembled at once:
           - Chart from chartConfig
           - Summary + raw table inside expanded "View raw results"
```

### Changes Required

**1. `agentic_loop.go` — Fix batch ordering (bug fix)**

In the `respond_to_user` handler within the tool-call processing loop: when `pendingFinal != nil`, check whether a `render_chart` tool call exists later in the same batch. If it does, **do not consume `pendingFinal`** — let the loop continue so `render_chart` can process it with its chart config.

When Summarize is ON, a `respond_to_user` that finds `pendingFinal` should be a complete no-op for rendering: log it in the transcript and move on. The chart handler and end-of-loop fallback are the only things that should ever consume `pendingFinal` and call `render()`.

**2. `sql_execution.go` — Move summary into the expander (rendering change)**

In `ToHTML()`, when both `HasChart` is true and `Summary` is non-empty, emit the summary text **inside** the `<details>` block, above the raw table, instead of as a separate top-level `<div class="markdown-content">` before the expander.

The `<details>` block becomes:

```
<details class="results-details">
  <summary>View raw results (N rows)</summary>
  <div class="markdown-content">{summary}</div>    ← summary moved here
  <div>{raw table HTML}</div>
</details>
```

The separate top-level markdown-content div for the summary is removed in this case.

**3. `summarizeResults()` prompt — Update context text**

The summarization prompt currently says *"you are summarizing the full result, which the user sees below."* With the summary now living inside the expander alongside the data, this is actually accurate — the data *is* directly below. No prompt change needed — the existing wording works correctly with the new layout.

### Files Touched

| File | Change | Lines |
|---|---|---|
| `pkg/services/agentic_loop.go` | `respond_to_user` handler: check for batched chart before consuming pendingFinal | ~12 |
| `pkg/services/sql_execution.go` | `ToHTML()`: move summary into `<details>` when HasChart + Summary | ~15 |

### What Does Not Change

- The `render()` method on `pendingFinalResult` — still calls `summarizeResults()` then `renderToolQueryResults()` as before
- The `summarizeResults()` function — same LLM call, same prompt
- The `renderToolQueryResults()` function — summary is still passed through to `AssistantResponse`, only the `ToHTML()` rendering of it changes
- The system prompt — no new instructions about summarization are needed
- `respondText` discard logic — remains as-is (intentional when Summarize is ON)
- The frontend (`ConversationView.svelte`) — no changes; it already renders chart first, then message HTML

- [ ] **Three-tool batch (query + respond + chart):** chart renders with Summarize ON (both tool orderings)
- [ ] **Two-tool batch (query + chart):** chart renders, summary inside expander
- [ ] **Two-tool batch (query + respond):** summary alone, table not collapsed, no chart — as before
- [ ] **Summarize ON + Chart ON:** chart at top, summary + raw table inside expander
- [ ] **Summarize ON + Chart OFF:** summary above table (not collapsed) — unchanged behavior
- [ ] **Summarize OFF + Chart ON:** chart at top, raw table collapsed — unchanged behavior
- [ ] **Summarize OFF + Chart OFF:** normal text + table — unchanged behavior
- [ ] **Summarize ON + respond_to_user without final query:** rejected with `summarization_requires_final_query`
- [ ] **Summarize ON + query error:** rejected with `query_error_requires_retry`
- [ ] **LLM providers:** OpenAI, Anthropic, Ollama
- [ ] **Dark mode / light mode:** chart and expander visible in both

## 7. Risk/Reward Analysis (per AGENT_READ_FIRST.md §4.4)

This change touches `agentic_loop.go` and `sql_execution.go`, both flagged in
§4.2 as requiring a documented risk/reward analysis before implementation.
The completed analysis below follows the §4.4 template and should be
appended to `RISK_ANALYSIS_LOG.md` once implemented, alongside the related
prior entries: *"Fix: Double Answer in Single Chat Bubble (respond_to_user
+ Summarization)"* and *"Fix: Collapsible Table Lost After Summarization
Fix"* (both 2026-08-10), which established the precedent that summarization
replaces `respondText` by design and that `ToHTML()` owns the collapsible
`<details>` rendering. This proposal extends, rather than contradicts,
that precedent.

- **Change:** (1) In the `respond_to_user` tool-call handler in
  `agentic_loop.go`, check whether a `render_chart` call exists later in the
  same batch before consuming `pendingFinal`; if so, defer so `render_chart`
  can consume it with the real chart config instead of an empty one.
  (2) In `ToHTML()` in `sql_execution.go`, when both `HasChart` and `Summary`
  are present, move the summary text inside the `<details>` block alongside
  the raw table instead of rendering it as a separate top-level div above
  the chart's collapsed table.

- **Fundamental goal impact:** **Improves answer delivery, does not touch
  answer accuracy.** Neither change modifies SQL generation, the LLM prompt
  sent for query construction, or the summarization prompt's content. The
  chart-loss bug currently causes the LLM's rendered chart to silently
  disappear for the user roughly half the time it batches all three tools —
  this is a direct failure of "the answer feels reliable" without any
  underlying data being wrong. The `ToHTML()` change is a pure rendering
  reposition; it does not change what data is shown, only where.

- **Risk category(ies):** Answer delivery, UX/Comfort, Regression.

- **Failure mode(s):**
  1. **Batch-check miscounts tool call position.** If the index tracking in
     the `respond_to_user` handler is implemented incorrectly (e.g., off-by-one
     when scanning for a later `render_chart`), a legitimate two-tool batch
     (query + respond only, no chart) could be mistakenly deferred and never
     rendered. Mitigation: the scan only looks for `render_chart` by tool
     name in the remaining slice of the same batch — if none exists, the
     existing consume-and-return path is unchanged. This must be covered by
     the two-tool (query+respond) regression test in §6.
  2. **`ToHTML()` reposition breaks users who have Summarize ON but
     VizEnabled OFF.** The `HasChart` flag gates this change — if `HasChart`
     is false, `ToHTML()` retains its current behavior (summary above the
     table, table not collapsed). This must be explicitly regression-tested,
     not assumed.
  3. **A model that never batches `render_chart` with the final query** (e.g.,
     calls it in a separate round after `respond_to_user` has already fired)
     hits the existing `render_chart_no_pending` rejection path — unaffected
     by this change, since `pendingFinal` was already consumed by that point.
     This is pre-existing behavior, not a new failure mode introduced here.
  4. **Provider-specific tool-call ordering differences.** OpenAI, Anthropic,
     and Ollama may order batched tool calls differently. Mitigation: the fix
     is deliberately order-independent — it works regardless of whether
     `render_chart` appears before or after `respond_to_user` in the array,
     which is the entire point of the fix. Must be verified against all three
     providers per §6.

- **Reward:** Eliminates a silent, non-deterministic failure where a chart
  the LLM explicitly generated does not appear to the user roughly half the
  time, for every conversation with both Summarize and Data Visualization
  enabled. Restores a coherent visual hierarchy where the summary sits next
  to the data it describes rather than being separated by a click-to-expand
  boundary. Affects any user who enables both settings together — likely a
  common combination for users who want both a visual and a narrative
  takeaway from their data.

- **Mitigations:**
  - No schema changes. No data source interaction — this is purely
    presentation-layer logic downstream of an already-executed, already-safe
    `SELECT` query.
  - No change to the LLM prompt or tool descriptions — the model's behavior
    and instructions are untouched; only how the backend assembles the
    already-returned tool calls into a final render changes.
  - `respondText` discard logic during summarization is unchanged — this
    proposal does not reopen or alter the settled design from the 2026-08-10
    "Double Answer" fix.
  - Full regression matrix in §6 covers all four Summarize × VizEnabled
    combinations, both tool-call orderings, and all three LLM providers.
  - Changes are small and isolated (~12 lines in `agentic_loop.go`, ~15 lines
    in `sql_execution.go`), keeping the diff reviewable and the blast radius
    contained to the two functions named above.

- **Decision:** Proceed. The chart-loss bug is a clear, demonstrable defect
  in answer delivery reliability with no offsetting risk to answer accuracy,
  data safety, or data integrity — the two highest-priority categories in the
  charter's goal order (§0). The UX reposition is a low-risk, additive
  clarification of existing behavior, gated behind the same `HasChart` flag
  already in use. Per §4.2, this analysis must be appended to
  `RISK_ANALYSIS_LOG.md` before or alongside implementation, and the
  **Resolution** field added once verified, following the pattern set by the
  existing 2026-08-10 entries above.
