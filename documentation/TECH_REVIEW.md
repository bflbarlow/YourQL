## 1. Architecture & Structure

### 1.1 God-Object `app.go` (~650 Lines)

`app.go` serves as the single Wails binding point and contains *everything*: forty-plus delegate methods, all frontend-facing type definitions, conversion logic, and helper functions. The types defined here belong in their respective domain packages:

```go
// Defined in app.go — should be in pkg/models/ or pkg/services/
type LLMProviderSetting struct { ... }
type DataSourceSetting  struct { ... }
type SchemaPreview      struct { ... }
type SchemaTablePreview struct { ... }
type SchemaColumnPreview struct { ... }
type QueryResult        struct { ... }
type GeneralSettings    struct { ... }
```

Additionally, `QueryResult` is duplicated: `app.go` defines one version for the user-accessible `ExecuteQuery` endpoint, while `pkg/services/sql_execution.go` defines a *different* `QueryResult` (with a `RowCount` field) used internally. These should be unified into a single definition in `pkg/models/`.

**Recommendation:** Split into domain-specific binding files:

```
bindings_conversations.go
bindings_datasources.go
bindings_llm_providers.go
bindings_skills.go
bindings_google_sheets.go
bindings_general.go
```

Each should be thin — validate inputs, delegate to services, and marshal responses.

### 1.3 Global Mutable Database Handle

`pkg/models/database.go` exposes a package-level variable:

```go
var DB *sql.DB
```

Every service function across the codebase reaches directly into this global:

```go
// in pkg/services/conversation.go
result, err := models.DB.Exec("INSERT INTO conversations (...) VALUES (...)", ...)
rows, err := models.DB.Query("SELECT ... FROM conversations ...", ...)
```

This has three consequences:

1. **Testing is impossible.** You cannot inject a test database or mock connection. Every function that touches `models.DB` is untestable in isolation.
2. **Tight coupling.** The services package is bound to both the `models` package and the `sql.DB` concrete type with no abstraction layer.
3. **Single-connection assumption.** `SetMaxOpenConns(1)` is set at startup; concurrent operations may contend.

**Recommendation:** Replace with dependency injection. The minimal change is to pass `*sql.DB` explicitly:

```go
type ConversationService struct {
    db *sql.DB
}

func NewConversationService(db *sql.DB) *ConversationService {
    return &ConversationService{db: db}
}

func (s *ConversationService) ListConversationsByUser() ([]*models.Conversation, error) {
    rows, err := s.db.Query("SELECT ...")
    // ...
}
```

A more thorough approach would define repository interfaces behind each service.

> **⚠️ Breaking-change note:** `app.go` currently calls bare package-level functions directly (e.g. `services.ListConversationsByUser()`, `services.CreateConversation(...)`), not methods on a struct. Introducing `db *sql.DB` as a field on service structs means **every one of the ~50 delegate calls in `app.go` must be updated** to go through an instantiated service (e.g. `a.conversationService.ListConversationsByUser()`), and `App` must be extended to hold and initialize those service instances at startup. This is a global, mechanical change — safe if done in one pass with a full rebuild, but not a localized edit. Do it as its own PR before/separate from other refactors so a compile failure is easy to bisect.

### 1.4 No Data-Access Service Interfaces

Outside of the LLM and database-driver abstractions, there are no interfaces for the data-access and business-logic layers. The codebase does define three interfaces, but they are narrow and each covers only one subsystem:

```go
// pkg/services/llm_client.go — LLM provider abstraction
type LLMClient interface {
    ChatCompletion(ctx context.Context, messages []ChatMessage) (string, error)
    ChatCompletionWithPayload(ctx context.Context, messages []ChatMessage) (content, requestJSON, responseJSON string, err error)
}

// pkg/services/db_driver.go — database driver abstraction (enables multi-DB support)
type DBDriver interface {
    TypeKey() string
    OpenDriver() string
    BuildDSN(conn *models.DataSource) (string, error)
    GetSchema(conn *models.DataSource) (*DataSchema, error)
    DisplayName() string
    SQLDialectHint() string
    DefaultPort() int
}

// pkg/services/db_driver.go — optional native query interface (BigQuery etc.)
type NativeQuerier interface {
    QueryRowsNative(conn *models.DataSource, query string) ([]string, [][]interface{}, error)
    PingNative(conn *models.DataSource) error
    CloseNative(conn *models.DataSource) error
}
```

The `DBDriver` interface is actually the most important abstraction in the codebase — it is what enables the nine-database-type plugin architecture. However, everything else — conversation CRUD, data source management, query execution, skill management — operates on concrete types and the global `models.DB` with no interface separating the service layer from the data-access layer.

**Recommendation:** Define interfaces for each service domain. For example:

```go
// Preserve existing function names as method names to avoid renaming every
// call site across app.go and discussion_engine.go. Do NOT rename
// GetConversationByID -> GetByID, SoftDeleteConversation -> SoftDelete, etc.
// unless you are prepared to update every caller in the same change.
type ConversationRepository interface {
    CreateConversation(title string, llmProviderID, dataSourceID *uint) (*models.Conversation, error)
    GetConversationByID(id uint) (*models.Conversation, error)
    ListConversationsByUser() ([]*models.Conversation, error)
    UpdateConversation(id uint, title *string, status *string, llmProviderID, dataSourceID *uint) (*models.Conversation, error)
    SoftDeleteConversation(id uint) error
}
```

> **⚠️ Breaking-change note:** The example above intentionally keeps the current function names as method names. The original draft of this recommendation used different names (`GetByID`, `ListActive`, `SoftDelete`), which — if adopted literally — would require renaming every call site in `app.go` and `discussion_engine.go`. Introduce the interface first with identical names to the existing functions; rename only as a separate, deliberate follow-up if desired.

### 1.6 Go Module Name Violates Convention

```go
module YourQL
```

Go module names should be lowercase and typically include a repository path for importability:

```
module github.com/yourorg/yourql
```

The current name does not prevent builds but breaks `go install`, makes the project un-importable as a library, and violates the [Go module naming convention](https://go.dev/doc/modules/managing-dependencies#naming_module).

> **⚠️ Breaking-change note:** This is *not* a one-line fix. All 27 Go files that import internal packages reference the literal path `"YourQL/pkg/..."`:
> ```go
> import (
>     "YourQL/pkg/models"
>     "YourQL/pkg/services"
> )
> ```
> Renaming the module requires a coordinated find-and-replace of every import statement in the same commit as the `go.mod` change, or the build fails immediately. Use `gofmt -w` / `goimports` after a scripted replace, and run `go build ./...` before committing.

## 2. Security

### 2.1 Plaintext Password Storage

`models.DataSource.Password` is stored directly in the local SQLite database file:

```go
type DataSource struct {
    // ...
    Password   *string   `json:"-"`
    // ...
}
```

The `json:"-"` tag prevents it from being serialized to the frontend, but the password is written in cleartext to `~/.yourql/yourql.db`. Anyone with filesystem access to the user's machine can read all stored database credentials.

**Recommendation:** On macOS, use the Keychain (`github.com/keybase/go-keychain`). On Linux, use `libsecret` (already an indirect dependency via Wails). On Windows, use the Credential Manager. Store only a reference/identifier in SQLite and retrieve the actual credential from the OS keychain at connection time.

> **⚠️ Breaking-change / migration note:** This is a **data-migration change, not just a code change.** Existing installs already have plaintext passwords in `~/.yourql/yourql.db`. Switching straight to "store only a reference" will orphan every existing `DataSource` and `LLMProvider` row — their `password`/`api_key` columns will still contain plaintext, but the new code will expect a keychain reference and fail to connect. A safe rollout requires:
> 1. A one-time migration on startup that reads existing plaintext values, writes them into the OS keychain, and replaces the DB column with a reference ID.
> 2. Handling the case where the keychain is unavailable (e.g., running headless/CI, Linux without a Secret Service provider) — fall back to the existing plaintext behavior rather than hard-failing, or the app becomes unusable on some Linux setups.
> 3. Testing on all three target OSes before shipping, since keychain APIs differ significantly in error semantics.

### 2.2 API Keys in Log Output

`pkg/services/llm_openai.go` logs the full request body:

```go
log.Printf("[OpenAI] Sending request to %s/chat/completions: %s", c.baseURL, string(jsonData))
```

While the API key is in the `Authorization` header (not the JSON body), this log entry includes the full prompt, model selection, and messages. If logs are persisted or forwarded, this leaks potentially sensitive prompt content including database schemas and user questions.

> **Correction:** This specific pattern is confined to `llm_openai.go` only. `llm_local.go` and `llm_anthropic.go` do **not** contain equivalent `log.Printf` calls with request bodies as of this review — verified by inspection, no matches found. Do not spend effort "fixing" those two files for this issue; only `llm_openai.go` needs the change. (Both files do send the API key via `Authorization`/`x-api-key` headers, so the general guidance to avoid logging headers still applies if logging is added there in the future.)

**Recommendation:** Remove or truncate. At minimum, log only metadata:

```go
log.Printf("[OpenAI] Sending request to %s/chat/completions — model=%s, messages=%d, tokens=~%d",
    c.baseURL, c.model, len(messages), approxTokens)
```

### 2.3 Raw HTML Generated in Backend, Rendered Unsafely in Frontend

`pkg/services/sql_execution.go` constructs HTML strings with embedded inline JavaScript event handlers:

```go
// Lines ~380–390 of sql_execution.go (inside formatResultsHTML)
sb.WriteString(fmt.Sprintf(
    `<button class="sql-toggle-btn" onclick="toggleSQLSection(this, 'sql-popover-%d')" ...>SQL</button>`,
    hash,
))
sb.WriteString(fmt.Sprintf(
    `<button class="copy-sql-btn" onclick="copySQL('sql-code-%d')" ...>Copy</button>`,
    hash,
))
sb.WriteString(fmt.Sprintf(
    `<button class="csv-btn" onclick="exportCSV(this, %d)" ...>↓ CSV</button>`,
    result.RowCount,
))
```

The frontend then renders these without sanitization:

```svelte
<!-- ConversationView.svelte -->
<div class="assistant-message">{@html message.content}</div>
```

This architecture has several problems:

- **XSS risk:** If any user-controlled data (column names, SQL text, result values) is not properly escaped, it could inject arbitrary HTML/JS into the rendered page.
- **CSP incompatibility:** Inline `onclick` handlers require `'unsafe-inline'` in the Content Security Policy, disabling a key browser security feature.
- **Tight backend/frontend coupling:** The Go backend must know the exact element IDs, CSS class names, and JavaScript function signatures that the Svelte frontend expects. Changing the frontend requires changing the backend.
- **Debugging difficulty:** JavaScript errors from these event handlers originate from `innerHTML` assignments, making stack traces unhelpful.

While `html.EscapeString` is called on individual cell values, the overall pattern is fragile. A single missed escape in a future code change opens an injection vector.

**Recommendation:** Return structured data from the backend and let the frontend render it:

```go
type AssistantMessageData struct {
    Explanation  string        `json:"explanation"`
    SQL          string        `json:"sql"`
    Columns      []string      `json:"columns"`
    Rows         [][]any       `json:"rows"`
    RowCount     int           `json:"row_count"`
    Exploration  []ExplorationResult `json:"exploration,omitempty"`
    ChartConfig  json.RawMessage `json:"chart_config,omitempty"`
    Summary      string        `json:"summary,omitempty"`
}
```

The Svelte component would then iterate over this data and render it with proper framework bindings and event handlers — no `{@html}` needed.

> **⚠️ Breaking-change / data-migration note:** This change is larger than it looks and affects **persisted data**, not just code:
> 1. `conversation_messages.content` currently *stores the rendered HTML string itself* (see `renderSQLResults` → `assistantResp.ToHTML()` → `CreateConversationMessage(..., assistantMessageHTML, ...)`). Every existing assistant message in every user's local SQLite database is already HTML. Switching the backend to emit structured JSON instead of HTML means:
>    - **Old messages** (HTML strings) and **new messages** (JSON payloads) will coexist in the same `content` column after the change ships.
>    - The frontend must detect which format it's looking at (e.g., via the existing `metadata.content_type` field, which is already used for `"html"` vs. absent) and render accordingly, or old conversations will show broken JSON as raw text.
> 2. This is a coordinated frontend+backend change — shipping the backend change alone breaks the frontend (it expects HTML in `{@html message.content}`), and shipping the frontend change alone breaks on the HTML the backend still sends. These must land together, ideally behind a `content_type` discriminator that already exists in the `metadata` JSON (`{"content_type": "html"}`) — extend it to `{"content_type": "structured"}` for new messages rather than assuming a single global format.
> 3. `formatSQLResultsForLLM` (used to feed prior results back into the LLM context on subsequent turns) currently parses the *separate* `sql_results` JSON column, not the HTML `content` column, so LLM context-building is unaffected by this change — only the rendering path is.

### 2.4 `window` Global Namespace Pollution

To make the inline `onclick` handlers work, `ConversationView.svelte` assigns functions directly to the `window` object:

```js
window.toggleSQLSection = function(btn, sectionId) {
    const section = document.getElementById(sectionId)
    // ...
}

window.copySQL = function(codeId) {
    const code = document.getElementById(codeId)
    navigator.clipboard.writeText(code.textContent).then(...)
}

window.exportCSV = function(btn, rowCount) {
    const table = btn.closest('.results-card')?.querySelector('.result-table')
    // ...
}
```

This pollutes the global namespace and means multiple conversation views in the same page context would conflict. In a Wails app this is unlikely (single window), but it's still an anti-pattern.

> **Additional finding (verified in code):** This is worse than a single isolated instance of the anti-pattern. `frontend/src/main.js` **independently defines its own `window.copySQL`** (a different implementation, using `document.querySelector('[onclick="copySQL(...)"]')` to find the triggering button) and `window.toggleSQLPopover`. `ConversationView.svelte` then **overwrites `window.copySQL` with a second, different implementation** (using `.closest()`/`.parentElement` traversal) every time a `ConversationView` instance is created, and additionally defines `window.toggleSQLSection` and `window.exportCSV`, which have no equivalent in `main.js`. The two `copySQL` implementations silently shadow one another based on load/navigation order — `main.js`'s version is live only until the user's first visit to a conversation view, after which `ConversationView.svelte`'s version permanently wins for the rest of the app's lifetime. Additionally, `main.js`'s `toggleSQLPopover` appears to be orphaned: the HTML currently generated by `formatResultsHTML` in `sql_execution.go` calls `toggleSQLSection` (matching `ConversationView.svelte`), not `toggleSQLPopover`, so that function in `main.js` may already be dead code left over from an earlier HTML-generation scheme (`buildCollapsibleSQLBlockHTML` predates `formatResultsHTML`'s toolbar-based layout). This should be confirmed and removed as part of any cleanup, independent of the larger refactor.
>
> **Useful precedent already in the codebase:** `main.js` also contains a working event-delegation implementation for the results-table column sorting (`document.addEventListener('click', (e) => { const th = e.target.closest('th.sort-header'); ... })`), which does not rely on inline `onclick` or global function assignment. This is a good template to follow when migrating `copySQL`/`toggleSQLSection`/`exportCSV` to the delegation pattern described below, and confirms the pattern is already viable within this codebase's constraints.

**Recommendation:** Eliminate this entirely by adopting the structured-data approach above. If staying with the current approach temporarily, use event delegation on the messages container:

```js
messagesContainer.addEventListener('click', (e) => {
    const btn = e.target.closest('[data-action]')
    if (!btn) return
    switch (btn.dataset.action) {
        case 'toggle-sql': /* ... */ break
        case 'copy-sql':   /* ... */ break
        case 'export-csv': /* ... */ break
    }
})
```

> **⚠️ Breaking-change note:** The snippet above is illustrative, not a drop-in fix. It depends on `data-action="toggle-sql"` etc. attributes that **do not exist** in the HTML currently generated by `formatResultsHTML` in `pkg/services/sql_execution.go` (which emits `onclick="toggleSQLSection(...)"` instead). Adopting event delegation therefore requires changing **both** sides:
> 1. The Go HTML generator must emit `data-action="..."` attributes (and drop the `onclick="..."` attributes) instead.
> 2. The frontend delegation handler must be added.
> Landing only one side leaves the buttons non-functional (either the attributes are missing, or the `window.*` functions the old HTML still calls are removed). This is a smaller, more contained change than the full structured-data rewrite in §2.3, but it is still a two-sided change, not a frontend-only edit.

## 3. Error Handling & Resilience

### 3.1 Silently Swallowed Errors

Throughout the codebase, errors are discarded with `_`:

```go
// pkg/models/database.go
_, _ = DB.Exec("UPDATE conversations SET max_context_messages = 10 WHERE max_context_messages = 0")

// pkg/services/discussion_engine.go
_, _ = models.DB.Exec("UPDATE queries SET data_source_id = ? WHERE id = ?", dbConnection.ID, query.ID)

// main.go
if err := godotenv.Load(); err != nil {
    log.Println("No .env file found, skipping")
}

// pkg/services/conversation.go — rows.Scan returns an error that is silently discarded
for rows.Next() {
    var c models.Conversation
    err := rows.Scan(...)
    if err != nil {
        continue  // row silently dropped, no log, no indication
    }
}
```

The last case is particularly problematic: if a `Scan` fails due to a schema mismatch (e.g., a column doesn't exist in the struct), rows are silently dropped with no way to diagnose why conversations are "missing."

**Recommendation:** At minimum, log these. Better: propagate or surface to the user where appropriate.

```go
if err := rows.Scan(...); err != nil {
    log.Printf("WARNING: failed to scan conversation row: %v", err)
    continue
}
```

### 3.2 `println()` Instead of Structured Logging

Multiple entry points use `println()`:

```go
// main.go
println("Error:", err.Error())

// app.go
println("Database error:", err.Error())
```

(`fmt.Printf` also appears once in `pkg/models/database.go` for a startup message — `fmt.Printf("Connected to SQLite database at: %s\n", dbPath)` — but not in `main.go` or `app.go`.)

`println` writes to stderr without timestamps, levels, or structure. For a desktop app this might seem acceptable, but it means:
- No way to filter by severity during debugging
- No structured fields for log analysis
- Inconsistent with the rest of the codebase which uses `log.Printf`

**Recommendation:** Adopt `log/slog` (standard library since Go 1.21) throughout:

```go
slog.Error("database error", "error", err)
slog.Info("connected to SQLite", "path", dbPath)
```

### 3.3 No-Operation Cancel Functions

```go
// app.go
func (a *App) CancelGoogleSheetsAuth(dataSourceID uint) error {
    return nil
}

func (a *App) CancelGoogleSheetsAuthTemp(sessionID string) error {
    return nil
}
```

These are misleading. The frontend calls them expecting cancellation, but the OAuth loopback server continues running. If the user initiates auth, closes the dialog, and re-opens a new Google Sheets connection, stale callback handlers may still be registered via `EventsOn`.

**Recommendation:** Implement actual cancellation using a `context.Context` that is stored and can be cancelled. Alternatively, track active auth flows in a map and clean up on cancel:

```go
type App struct {
    ctx          context.Context
    activeAuths  map[string]context.CancelFunc
    authMu       sync.Mutex
}
```

### 3.5 Default-Retryable Error Handling

`isRetryableError` in `sql_execution.go` defaults to `true`:

```go
func isRetryableError(err error) bool {
    msg := err.Error()

    // Check fatal patterns — return false
    // ...

    // Check retryable patterns — return true
    // ...

    return true  // <-- Everything else is assumed retryable
}
```

This means any unrecognised database error triggers a retry loop of up to `maxRetries+1` attempts. A permanent error (e.g., permission denied on a specific table, schema mismatch) will waste LLM API calls retrying a query that will never succeed.

**Recommendation:** Default to non-retryable and only retry on explicitly known-recoverable errors:

```go
return false  // default: don't retry unknown errors
```

> **⚠️ Behavior-change note (not a code-breaking change, but a functional regression risk):** Flipping this default will change observed behavior for any error message that doesn't match one of the existing `fatalPatterns`/`retryablePatterns` substrings. Today, unmatched errors are retried (arguably too permissive); after the change, unmatched errors will fail immediately on the first attempt (arguably too strict, for drivers/error strings not yet covered by the pattern lists — e.g. a new SQL Server or Snowflake error phrasing that isn't in either list). Before flipping the default, audit the `retryablePatterns` list against errors actually seen from each supported driver (MySQL, Postgres, SQL Server, Snowflake, BigQuery, SQLite, CSV/Excel/Sheets) to avoid making legitimately-transient errors (e.g. a driver-specific lock-wait phrasing not yet in the list) permanently unretryable. Consider logging a warning when the default path is hit, to surface gaps in the pattern lists during a transition period rather than flipping blind.

### 3.6 Trap-Pattern Deferred Error Handler

The `defer` in `ProcessUserMessage` is a deferred error-handler that writes an assistant error message if the function returns with a non-nil error:

```go
assistantMessageSaved := false
defer func() {
    if err != nil && !assistantMessageSaved {
        errorMsg := fmt.Sprintf("I encountered an error: %s", err.Error())
        _, _ = CreateConversationMessage(conversationID, "assistant", errorMsg, nil, nil, nil)
    }
}()
```

This uses a boolean flag (`assistantMessageSaved`) to track whether an error message was already written. This pattern is fragile by construction: every new branch added to `ProcessUserMessage` in the future must remember to set the flag before returning, or a duplicate error message can be written. It is a maintainability/robustness concern rather than a currently-reproducing bug — tracing the two call sites of `executeFinalQueryWithRetry` in the current code shows `assistantMessageSaved = true` is in fact set immediately after each call, before the enclosing function returns, so no double-message currently occurs. The risk is that this invariant is easy to break silently in future edits, not that it is broken today.

**Recommendation:** Refactor `services.ProcessUserMessage` in `discussion_engine.go` to avoid the deferred flag-tracking pattern. Instead of a `defer` that conditionally writes an error message based on a mutable boolean, handle errors explicitly at each return point, or extract the error-message-writing into a named helper that is called before each `return`:

```go
// Example refactored pattern for services.ProcessUserMessage:
// Replace the defer + assistantMessageSaved flag with explicit calls
// at each error return point:
func saveErrorAndReturn(conversationID uint, err error) error {
    errorMsg := fmt.Sprintf("I encountered an error: %s", err.Error())
    _, _ = CreateConversationMessage(conversationID, "assistant", errorMsg, nil, nil, nil)
    return err
}

// Then at each error return in ProcessUserMessage:
//   return saveErrorAndReturn(conversationID, fmt.Errorf("failed to get conversation: %w", err))
// And at each success return where a message was already written:
//   return nil  // no defer needed — the flag is gone
```

### 4.4 `VizChart.svelte` Registers Chart.js Globally at Module Scope

```js
import { Chart, registerables, Colors } from 'chart.js'
Chart.register(...registerables, Colors)
Chart.defaults.borderColor = '#e9ecef'
Chart.defaults.font.family = 'system-ui, -apple-system, sans-serif'
```

This runs when the module is first imported, regardless of whether any chart is ever rendered. It mutates global Chart.js defaults and adds all controllers, elements, scales, and plugins to the registry. In a conversation with 50 messages and zero charts, this is wasted work.

**Correction — do not simply remove the `register()` call.** An earlier draft of this recommendation suggested Chart.js "auto-registers" and that the explicit call could be dropped. That is **incorrect for the import path this project uses** and would break every chart type (bar, line, pie, doughnut, scatter, radar, polarArea — all listed as supported in the LLM system prompt in `discussion_engine.go`). Verified against the installed `chart.js@4.5.1` package:

- `import { Chart, registerables } from 'chart.js'` (what `VizChart.svelte` uses) requires an explicit `Chart.register(...)` call. Nothing is auto-registered on this path.
- Auto-registration only happens via the *separate* entry point `chart.js/auto`, which internally does exactly `Chart.register(...registerables)` for you. The project does not import from `chart.js/auto`.

Removing `Chart.register(...registerables, Colors)` without importing from `chart.js/auto` instead would cause every chart to fail at construction with a Chart.js "controller not registered" runtime error — a regression that might not be caught by manual testing if the tester only tries one chart type.

**Actual safe recommendation:** register only the specific controllers/elements/scales actually used by the seven documented chart types (`bar`, `line`, `pie`, `doughnut`, `scatter`, `radar`, `polarArea`), rather than the full `registerables` bundle. This reduces bundle size without removing needed registrations. However, the full `registerables` set also includes `Filler` (needed for `fill: true` on area/line charts), `Title` and `SubTitle` (needed if the LLM generates a chart config with titles), `Decimation` (for large datasets), and `TimeScale`/`TimeSeriesScale`/`LogarithmicScale` (needed for time-series and logarithmic axes — the system prompt explicitly mentions "line = time series, trends, sequential data"). Since the LLM is free to generate configs that use any of these features, the narrowed list must include them or those charts will silently render without fills/titles/time-axes. A safe narrowed set is:

```js
import {
  Chart,
  BarController, LineController, PieController, DoughnutController,
  ScatterController, RadarController, PolarAreaController,
  BarElement, LineElement, PointElement, ArcElement,
  CategoryScale, LinearScale, RadialLinearScale, TimeScale, LogarithmicScale,
  Legend, Tooltip, Colors, Filler, Title, SubTitle
} from 'chart.js'

Chart.register(
  BarController, LineController, PieController, DoughnutController,
  ScatterController, RadarController, PolarAreaController,
  BarElement, LineElement, PointElement, ArcElement,
  CategoryScale, LinearScale, RadialLinearScale, TimeScale, LogarithmicScale,
  Legend, Tooltip, Colors, Filler, Title, SubTitle
)
```

This still runs at module scope (registration is inherently a one-time global setup step in Chart.js's API design — that part of the original critique about "module-scope side effects" is accurate and unavoidable). The savings compared to `...registerables` are modest (only `BubbleController` and `Decimation` are excluded). Given the modest savings and the risk of silently breaking a chart feature the LLM might generate, **keeping the current `Chart.register(...registerables, Colors)` is the safest option** unless bundle size is a demonstrated problem. If narrowing, verify each of the seven chart types with fill, titles, and time-axes after the change, since a missed plugin (e.g. forgetting `Filler` for area charts, or `TimeScale` for time series) will silently break just that feature.

## 5. Database & Migrations

### 5.1 SQL Injection Risk in Migration Code

The `ensureColumn` function builds SQL via string interpolation:

```go
func ensureColumn(tableName, columnName, columnDef string) error {
    // ...
    _, err = DB.Exec(fmt.Sprintf("ALTER TABLE %s ADD COLUMN %s %s", tableName, columnName, columnDef))
    // ...
}
```

The arguments come from hardcoded constants in `migrate()`, so there's no immediate injection risk. The function is already unexported (`ensureColumn`, lowercase), so it cannot be called from outside the `models` package. However, it does not validate its inputs, so a future developer working within the `models` package could inadvertently pass unsanitized values.

**Recommendation:** Add input validation matching `^[a-zA-Z_][a-zA-Z0-9_]*$` for table and column names. (The function is already unexported, so no visibility change is needed.)

---

### 5.2 `runMigration` Error Handling Is Fragile

```go
func runMigration(name string, fn func() error) error {
    var existing string
    err := DB.QueryRow("SELECT name FROM schema_migrations WHERE name = ?", name).Scan(&existing)
    if err == nil {
        return nil // already applied
    }
    if err := fn(); err != nil {
        return fmt.Errorf("migration %s failed: %w", name, err)
    }
    _, err = DB.Exec("INSERT INTO schema_migrations (name) VALUES (?)", name)
    return err
}
```

There is a subtle bug here: if `fn()` succeeds but `INSERT INTO schema_migrations` fails (e.g., disk full), the migration will be re-attempted on the next startup. If the migration is not idempotent, this could corrupt data. The migration function and the bookkeeping insert should be wrapped in a transaction.

> **Caveat when implementing:** SQLite *does* support DDL (including `ALTER TABLE ADD COLUMN`/`DROP COLUMN`) inside a transaction, so wrapping `fn()` + the bookkeeping insert in a `sql.Tx` is safe and will work for the migrations currently defined (`migrateDbToDataSources`, the various `dropColumnIfExists` calls). However, `fn` closures in this codebase call the package-level `DB.Exec(...)` directly rather than accepting a `*sql.Tx`/`*sql.DB` parameter — the function signatures (`ensureColumn`, `columnExists`, `dropColumnIfExists`, and any custom migration like `migrateDbToDataSources`) would all need to be changed to accept and use a transaction handle instead of the global `DB` for this fix to actually provide atomicity. Wrapping `runMigration` in a transaction without also threading that transaction through to every helper it calls internally will not achieve the intended atomicity — the inner `DB.Exec` calls would still run outside the transaction on the global connection.

---

### 5.3 Single SQLite Connection

```go
DB.SetMaxOpenConns(1)
DB.SetMaxIdleConns(1)
```

While this avoids SQLite's "database is locked" errors in a single-writer scenario, it means every database operation serializes behind a single mutex. If a long-running query (e.g., schema introspection) holds the connection, UI operations (listing conversations) will block.

**Recommendation:** Use WAL mode (already enabled) which supports concurrent readers with one writer. Increase `SetMaxOpenConns` to at least 2–4.

## 6. Driver Architecture

### 6.1 `init()` Registration Is Fragile

Each driver file registers itself via `init()`:

```go
// db_postgres.go
func init() {
    RegisterDriver(&PostgresDriver{})
}
```

This relies on import side effects. If `db_postgres.go` is accidentally excluded from a build or its package isn't imported, the driver silently disappears with no compile-time error. The import in `main.go` is only through `pkg/services` (for `BuildDSN`), so if a driver file's `init()` panics, the app crashes at startup with no indication of which driver caused it.

**Recommendation:** Use explicit registration in a central location:

```go
// pkg/services/drivers.go
var AllDrivers = []DBDriver{
    &MySQLDriver{},
    &MariaDBDriver{},
    &PostgresDriver{},
    &SQLiteDriver{},
    &RedshiftDriver{},
    &SQLServerDriver{},
    &SnowflakeDriver{},
    &BigQueryDriver{},
    &GoogleSheetsDriver{},
    // must include all 9 drivers currently registered via init() — see list below
}

func init() {
    for _, d := range AllDrivers {
        RegisterDriver(d)
    }
}
```

> **⚠️ Breaking-change note:** This is a full inventory change, not an illustrative snippet to adapt loosely. There are currently **nine** drivers registered via individual `init()` functions, one per file: `MySQLDriver`, `MariaDBDriver`, `PostgresDriver`, `SQLiteDriver`, `RedshiftDriver`, `SQLServerDriver`, `SnowflakeDriver`, `BigQueryDriver`, and `GoogleSheetsDriver`. If the per-file `init()` functions are removed in favor of a central list, **every single driver must be added to that list**, and the central list itself still needs its own `init()` (or an explicit call from `main.go`/`app.go` startup) that actually calls `RegisterDriver` for each entry — declaring the slice alone does nothing. Missing even one driver from the list, or forgetting the registration loop, will cause that data source type to silently disappear from `GetSupportedDBTypes()` and fail with "unsupported database type" at runtime for any user who has an existing connection of that type configured. Test by asserting `len(driverRegistry) == 9` (or equivalent) after startup, or by checking `GetSupportedDBTypes()` returns all expected types, before shipping this change.

## 7. Frontend-Specific Issues

### 7.1 `@html` Usage Without Sanitization

```svelte
<div class="assistant-message">{@html message.content}</div>
```

Svelte's `{@html}` is explicitly documented as dangerous. It bypasses all framework XSS protections. While the backend escapes values with `html.EscapeString`, this is a single point of failure: if any future change adds unescaped content to the HTML generation, the frontend will render it.

**Recommendation:** As discussed in §2.3, return structured data and render with Svelte bindings.

---

### 7.2 Full Message List Re-fetched After Every Send

```js
async function handleSendMessage() {
    // ...
    await ProcessUserMessage(activeConversation.id, msgToSend)
    conversationMessages = await GetConversationMessages(activeConversation.id)  // re-fetches all
}
```

After sending a message, the *entire conversation history* is re-fetched from the backend. This is wasteful — only the new assistant message(s) need to be appended. As conversation length grows, this becomes increasingly expensive.

**Recommendation:** After `ProcessUserMessage` returns, fetch only new messages (by ID > last known ID) or have the backend return the new messages directly from `ProcessUserMessage`.

---

### 7.3 Processing Phase Listener Registered at Module Scope

```svelte
<script>
  import { EventsOn } from '../wailsjs/runtime/runtime.js'

  EventsOn('processingPhase', (phase) => {
    processingMessage = phase
  })
  EventsOn('processingComplete', () => {
    processingMessage = ''
  })
  // ... later imports
</script>
```

`EventsOn` is called at the top of the component's `<script>` block (component-instance scope, not true module scope — it re-runs each time `App.svelte` is instantiated), before `onMount`.

> **Context check:** `App.svelte` is mounted exactly once, directly by `frontend/src/main.js` (`mount(App, { target: document.getElementById('app') })`), and is never conditionally rendered, unmounted, or re-created elsewhere in the codebase — it is the permanent SPA root for the lifetime of the window. So in the *current* codebase, this does not actually cause duplicate-listener accumulation in practice, since `App.svelte` never re-mounts. The recommendation below is worth adopting as defensive best practice (and is a no-risk, non-breaking change), but it is not fixing an active bug — it is guarding against a scenario (root component remount) that would only arise if the app's mounting strategy changes in the future (e.g., hot-module-reload during development, or a future refactor that conditionally re-mounts `App`).

## 9. Recommended Priority Order

If addressing these issues incrementally, the recommended order is below. Items are now annotated with their actual rollout complexity, since several are more involved than a first read suggests (see the linked sections for the full breaking-change analysis):

1. **Remove binary from git and update `.gitignore`** — genuinely low-risk for the working tree, but note (§4.9) that `.gitignore` alone doesn't purge history; a `git rm --cached` + optional history rewrite is a separate, coordinated step if repo size matters.
2. **Remove API key logging in `llm_openai.go` only** (§2.2) — true quick win, single file, no coordination needed. (Not needed in `llm_local.go`/`llm_anthropic.go` — corrected finding.)
3. **Add graceful shutdown via `OnShutdown`** (§3.4) — low-risk, additive change; verified `OnShutdown` is a real, supported Wails v2 option.
4. **Replace `{@html}` with structured data rendering** (§2.3) — highest-value fix for the most significant runtime risk, but requires a **coordinated backend+frontend change** landed together, plus a `content_type` discriminator so old HTML-format messages already stored in users' local databases keep rendering correctly. Do not ship the backend or frontend half alone.
